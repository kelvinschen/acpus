## Architecture gates to implement

Use a small repository-native Node check integrated with the existing check plan. Do not create a custom lint framework.

The A01 gate must enforce what can be enforced **without failing on intentional pre-migration debt**:

1. any declared `effect` or `@effect/vitest` v4 migration dependency uses the frozen exact RC (`4.0.0-rc.111`), not v3/beta/snapshot/range;
2. production/test application files do not import from `repos/effect`;
3. `effect/unstable/*` imports are rejected unless listed in an explicit migration allowlist; A01 allowlist is empty;
4. `repos/**` is not part of package exports, TypeScript project references, normal Vitest discovery, or Knip application graph;
5. the vendored Effect source manifest, once present, matches the frozen RC and commit-evidence file/packet expectation;
6. the check does not attempt to ban all existing `neverthrow` yet—A02–A05 own removal. It may report census information, but existing debt must not make A01 impossible to land.

Guardrail implementation should be based on stable structural checks (manifest/import/config inspection), not line-count baselines that become noisy after every migration commit.

## Stop-and-return conditions

Do not improvise around any of these. Stop the work package and return to Master if:

- either exact rc.111 package cannot be resolved from the configured registry;
- installed package types materially disagree with the vendored rc.111 source;
- the upstream commit does not contain rc.111 manifests as expected;
- isolating `repos/**` requires changing product build semantics rather than configuration/exclusions;
- a central v4 pattern appears to require `effect/unstable/*` for A01;
- implementing the gate would require modifying runtime business code.

A01 is ready because its cross-package decisions are frozen. The worker is responsible for implementation evidence, not for re-deciding the Effect release train or architecture.
