# Forked Run as the recovery path for broken Program Step scripts

When a long Run fails because a Program Step contains broken script (bad shell syntax, missing tool on PATH, wrong path, missing dependency), Node Retry against the same frozen snapshot cannot recover — the script is the bug. Authors need to edit the Workflow Spec and continue execution without losing upstream Agent Step transcripts, artifacts, and produced outputs.

## Decision

Acpus introduces a Forked Run: a new Run derived from a prior terminal Run (`completed`, `failed`, or `cancelled`) by supplying a possibly-modified Workflow Spec. The Forked Run scans the prior Run's Run Checkpoints in order and inherits each Node whose Node Key exists in the new Spec, whose prior state is `completed`, and whose Node Definition Hash (the canonical hash of the compiled IR Node, including the full subtree for Composite Nodes) matches. Inheritance stops at the first Node that fails any of these checks; that Node becomes the default Fork Origin and it plus everything after it executes fresh. The operator MAY override Fork Origin to force an earlier restart, but never to a Node inside a Composite's body. A Forked Run is its own Run with its own frozen snapshot — the prior Run is never mutated, preserving frozen-snapshot and Replay invariants. Inherited artifacts are physically copied into the Forked Run so the prior Run can be deleted independently. Run Observations include a Run's Forked Run lineage so `acpus runs list` can mark "forked from <prior-run-id>".

## Considered Options

- **Unfreeze a single failed Node within the same Run (P1).** Rejected: this breaks the `Run = frozen workflow snapshot` definition, breaks Replay's "same inputs reproduce same Node topology" invariant, and forces a new "partially mutable snapshot" mental model into every spec that references Run.
- **Force Node Retry to rerun the same broken script.** Rejected: by definition cannot recover from script bugs, which is the dominant authoring failure mode for AI-generated workflows.
- **Require authors to start a fresh Run from scratch.** Rejected: discards costly upstream Agent Step transcripts and ACP sessions accumulated across long agent loops.
- **Inherit purely on Node Key + Node type without a hash.** Rejected: lets silent content drift (a changed `cmd`, `prompt`, or `capture`) reuse stale outputs across structurally identical Nodes; the author who edited the Spec — usually an AI agent — is the least likely party to notice.
- **Require operator to specify Fork Origin explicitly.** Rejected: the inheritance boundary is mechanically derivable from checkpoint hash comparison; making it a required argument forces operators to predict what the system already knows.

## Consequences

Run Checkpoints become a first-class persistence concept: every terminal Node outcome is recorded with sequence, Node Key, state, Node Definition Hash, output, artifact references, and error summary. Continuation (the Agent Step mode that re-enters the same acpx ACP session) does not span Runs: a Forked Run starts fresh ACP sessions for any Agent Step it executes, including inherited ones it must re-enter. Forking when the prior Workflow's Spec is missing from the Workspace must fail rather than silently fall back to the prior frozen snapshot, otherwise Forked Run degrades into Node Retry. Reused outputs are accepted as historical facts even when they originally depended on prior `run_id`, `now()`, or other runtime context. Inherited Program Step side effects are assumed to still exist on disk; Acpus does not replay them. Node Retry remains for transient runtime errors against an unchanged Spec; Forked Run is the path when the Spec itself must change. Fork-of-fork is supported by treating any prior Run uniformly: lineage records only the immediate prior Run, not the full ancestor chain, so a Forked Run cannot be distinguished from a non-forked Run when it is later used as a prior Run.
